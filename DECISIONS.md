# DECISIONS.md

1. **Indexes.** I went with five indexes. A unique index on `emp_code` in the employees collection — that's a no-brainer for the uniqueness guarantee and fast lookups. A unique compound index on `(emp_code, date)` in attendance_logs to make sure there's only one record per employee per day and to handle the punch-in race condition at the database level. Then `(date desc, emp_code asc)` for the attendance listing sort order, a similar one with `status` as a prefix for status-filtered queries, and `(department, emp_code)` on employees for department filtering. I thought about adding a dedicated index on `(late_minutes, date)` for the leaderboard, but decided against it — the date-based index already handles the initial `$match` stage well enough, and one more index means slower writes for every punch-in. Not worth it at this scale.

2. **Punch-in race.** Say two identical punch-in requests come in at the exact same instant. Both pass validation, both look up the employee, both try to insert a document with the same `emp_code` and `date`. The unique compound index on `(emp_code, date)` means only one `insert_one` succeeds — the other throws a `DuplicateKeyError`. My code catches that and returns 409. There's no check-then-insert gap to exploit because the constraint is enforced by MongoDB itself, atomically.

3. **Ties.** I use `$setWindowFields` with `$rank`, which gives standard competition ranking — if two employees both have 45 late minutes and that puts them at rank 3, they both get rank 3 and rank 4 is skipped. The `limit` filter is `rank <= limit`, not a simple array slice, so if the tie happens right at the cutoff, both employees are included. The response might have more rows than `limit`, and that's intentional. Within the same rank, I sort by `emp_code` ascending so the order is deterministic.

4. **Headcount.** The department summary queries the `employees` collection separately to count people with `joined_on <= month_end`, grouped by department. This happens before I even touch the attendance logs. So someone who joined in January but hasn't punched in once all year still shows up in the headcount — which is exactly what R9 asks for. The headcount doesn't come from grouping logs, it comes from the employee records themselves.

5. **One thing I would change.** If this had to handle 100x the data, the analytics aggregations would start hurting. I'd introduce pre-computed monthly summary documents — every time someone punches out or a record gets corrected, update a running tally in a `monthly_summaries` collection. That turns the analytics reads from scanning thousands of records into a single document lookup. For the raw data, I'd shard `attendance_logs` on `{emp_code, date}` since it's already the unique key and gives good write distribution. The trend endpoint's `$densify` + per-day headcount lookup would also need rethinking — probably a materialized view or a cron job that pre-builds the daily snapshots.
